## Before you build anything: ask the owner, one question at a time

The owner makes the design calls. Every open question below must be put to them **before** the work it affects starts:

- **One question per message.** Wait for the answer before asking the next. Do not bundle them, and do not start building in between unless the answer clears a piece of work that depends on nothing still open.
- **In the order listed.** Earlier answers can change or remove later questions; skip a question the owner's answers have already settled, and say so.
- **Each question stands on its own:** say what it is about, what the options are, and your recommendation with one line of why. Plain words, no file names unless asked.
- **Record each answer here,** in the "Answer" column, with the date, before moving on. A decision recorded as "proposed" is not an answer.
- **Discuss when asked.** If the owner says "discuss first", or "understand first, build later", explain and wait; do not build.
- New questions found while working go to the end of the list and are asked the same way.

### How the spine fits the rest

- The narrator never sees the spine: only the current beat's intent, plus "Chapters so far" once milestones conclude.
- The observer never sees the spine either. The tracker sees ending titles, open criteria and the exchanges.
- A scene ends when the place changes or the planner's scene runs out of beats (`state.meta.sceneSerial`). A re-plan never ends one.
- Re-plan triggers from the spine are story events after the last plan (`spineTrigger`): a scene closed drifting, an ending lost a criterion, every ending turned away.

## Reassessment in light of what was built

The integration plan and the "considered" list were written on 17 November, before the spine, the tracker, the cast anchors, per-module profiles and parallel calls existed. Some of their assumptions no longer hold.

### Item 1 (memory providers): what changes

| Point | Then | Now | Recommendation |
| --- | --- | --- | --- |
| What the director sends as memory | Only summaries | Summaries **and** "Chapters so far" (concluded milestones), and "How they look" anchors | **Open question 3 (see the list at the top):** in `extension` mode, keep sending chapters? They are spine conclusions, not summaries, but a memory extension's summaries may tell the same events. Suggest: chapters stay in `director` and `extension`, go in `off` only if the owner wants silence |
| Who reads the observer's per-reply summaries | The narrator (via summaries) and the planner | Also the planner's fallback, and milestone conclusions draw on criteria quotes | Keep the per-reply summary in every mode, as planned; it matters more now |
| Tag stripping | Affects the observer and the record hash | Also affects the **tracker**: its quotes come from the same visible text, and a batch stands only while every covered reply's hash is unchanged | The old-hash compatibility in step 3 must cover `track.covers` hashes too, or switching stripping on voids every batch and the tracker re-reads them |
| Hidden messages | BaiBai Book hides old messages; the director treats them as out of the prompt | Both the observer (`nextUnread`) and the tracker (`nextBatch`) skip hidden replies | Fine in play: BaiBai keeps 15 recent messages visible, and the tracker reads every 4. On an existing chat, replies already hidden are never read; say so in the setting's explanation |
| Background calls per reply | "Two" (observer + BaiBai's summariser) | Observer every reply, tracker every N replies, BaiBai's summariser, plus conclusions and spine re-plans | Measure before recommending the pairing. Put the tracker on a cheaper profile; it then runs beside the observer |
| `location` and `time` in the notes | Open: keep or drop when a memory extension sends them | The director's location now decides **scene boundaries** for the spine state | Keep the director's own location; dropping it would break building / drifting. This settles the old open question |
| Planner prompt size | Provider text replaces the director's summaries | The planner now also carries the spine section, kind definitions and spine rules | Cap provider text (around 3,000 characters) and prefer BaiBai's injected-history slice if the full history is long |

### New interactions to know about

- **Cast changes do not reach other extensions.** Renaming, removing or locking a character changes only the director's record. BaiBai Book keeps its own NPC roster under the old name.
- **Multi-person cards** (one card, several people) are split only in the director; other extensions still see one card.
- **The spine tracker and a memory extension both read every reply** for different purposes. Neither knows about the other; there is no shared reading.

## Known limits, left as they are

- Renaming a character does not change old text that names them (facts, summaries, criteria).
- Record grouping is by name match only; a fact that says "he" lands under world facts.
- The role-name check is English-shaped (capital letters, "the / a / an").
- Appearance does not follow the story (a scar gained later); by design, editable by hand.
- Hiding a reply that belongs to a tracker batch drops that reply's spine findings.
- The Plan tab has one "unsaved changes" flag for all its forms.
